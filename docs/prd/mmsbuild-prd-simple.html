Start here

The goal: a website factory

Many businesses use it. They ask for a change. The change goes live with proof.

1AskA business asks for a change.
→
2BuildThe change gets made.
→
3ApproveThe right person says yes.
→
4Go liveIt appears on the real website.
→
5Prove itThe system checks the live site and keeps a record.
Example

Green Kitchen has a website. The owner says: "Add a page for our new salads."

The page is built. The owner approves it. It goes live. The system opens the live site, sees the page is really there, and saves a record.

  • "Proof" means a saved record. Not just someone saying "it's done".
  • "Many businesses" means hundreds of customers, each kept separate.
  • Today's sites (Sheeltron and others) are tests. They are not the final goal.

Never broken

The 4 rules

Everything in the plan must follow these. Rules 1 and 2 matter most.

1 · Own approver

Each website has its own approver. No master key.

2 · Stop if broken

If a safety check breaks, the change stops.

3 · One site each

One project = one domain = one website.

4 · One publisher

Only the CMS can make a site live.

Rule 1 — each website has its own approver

Not allowed

One master key

opens → Green KitchenCorner CafeShoe Shop

One key can say yes to every website. If it leaks, everything is at risk.

Required

One key per website

→Green Kitchen only
→Corner Cafe only
→Shoe Shop only

Green Kitchen's key works only on Green Kitchen. Like each shop having its own manager.

Rule 2 — if a check breaks, stop

Wrong: fails open

The checker crashes. The page goes live anyway.

Like a door that swings open when the power goes out.

Right: fails closed

The checker crashes. The page is stopped. You see "blocked", not "success".

Like a door that stays locked when the power goes out.

Lock the admin door

Today the admin page has no sign-in. Fix that first.

Today: door open

Anyone who finds the admin address can:

  • delete a website
  • create a machine key
  • read an existing key

Why first? Every later phase needs a safe admin area. Building on an open one means doing the work twice.

P4 Phase 4 · the biggest

Approvals with proof

The right person says yes. The system checks the live site. It keeps a record. It can undo.

Part A — finding the right approver

The system asks these questions, top to bottom.

1Does this website have its own approver?Yes → use them
2If not: does its business have one, and share it?Yes → use them
3If not: does its agency have one, and share it?Yes → use them
4Nobody found?✕ STOP. Nothing happens.

Add

Give a website its approver.

Share down

A business approver can cover its own sites. Never another business.

Swap

New approver works at once. The old one stops at once.

Remove

No approver means everything risky is refused.

Must be true first

Two systems handle approvals. One gives the yes. One checks the yes.

Both must agree who the approver is. If they disagree, a valid yes gets rejected.

Part B — two separate approvals

fileWebsite packageFixed. Can't change after approval.
→
approval 1Load into CMSNeeds its own yes.
→
pauseLook at itCheck what landed.
→
approval 2Make it liveA second, separate yes.
→
proofCheck + receiptOpen the live site. Save a record.

One yes can never cover both steps. That pause in the middle is on purpose.

Part C — when an approval is refused

No approval

Refused

Nobody said yes. Nothing loads.

Wrong file

Refused

The yes was for a different package.

Expired

Refused

The yes was too old. It lasts a few hours.

Already used

Refused

Each yes works once. Like a train ticket.

These refusals happen on the server. Having a password or machine key does not get around them.

Answered by the PRD

5 big questions

Should there be one publisher, or two?

One. Only the CMS publishes.

The design tool already has a good "is the site really live?" check. The CMS will borrow it, not build a new one.

Where are approval records kept?

In the approval system. Its records can't be edited.

Receipts go there too. The other side keeps its own separate copy. They are compared, never merged.

How are approvers added and changed?

Four actions: add, share down, swap, remove.

Both systems read the same approver list. A swap takes effect at once.

Can the design tool test on its own?

Yes. It gets its own practice website.

That practice site follows the same approval rules as a real one. Otherwise the test proves nothing.

Was the "no styles" site version 7?

No — version 4. Version 7 was the fix.

This matters. The pre-check limit is set using that example.
