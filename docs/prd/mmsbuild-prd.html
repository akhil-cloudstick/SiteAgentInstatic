1The goal

MMSBUILD is a governed website factory — sellable and runnable for many businesses, where a business asks for a change and it goes live with proof.

The current pilots exist to prove it works. They are not the objective. Every requirement below serves that one sentence; anything that does not is a non-goal.

Two decisions that are never traded away

Approval is a per-property configurable approver, not one platform key.

No check may fail open. A check that cannot run reports failure — never a zero-findings pass.

2Status of the six items claimed as already built

The brief asks that six items be treated as present. Each was checked against the working software. Two hold, three are partial in ways that change what the requirements must say, one is miscredited.

And all six are uncommitted

None of the six is deployed. "Built" and "running" are different claims, and the acceptance suite tests the second.

ClaimedVerdictWhat is actually there, and what is missing
Per-property approver key blocked The side that checks approvals can resolve a per-property approver and is tested for it. But the live policy carries no property entries, and the side that issues approvals verifies everything against one platform-wide identity — so it would refuse to issue a property-signed approval before the checking side ever saw it. No registration, no rotation.
Render-aware pre-flight partial Reports all four required items and computes them from the real publishing logic. But nothing blocks on its findings, and it runs only on import — the publish tools have no projection at all, and publishing is the step that renders.
Strict argument validation holds Enforced centrally before any tool runs, so no tool can forget it. Every tool schema was checked. A wrong or unknown setting now fails, naming the accepted set, instead of being silently discarded.
Revision stamp partial On the software and returned with an approved action's result — but absent from every durable record. Nobody reading a past deploy can say which build performed it, which is the reason the stamp was wanted.
Font install on the machine path holds Downloads the font files so published pages never call a third party, and is genuinely idempotent — an already-installed family with the same variants and subsets is skipped. A partial match re-installs with the union rather than destroying what was there.
Notify-on-creation miscredited Creation notification already shipped and is not new; what is new is notification on every message. Both are silently disabled unless a destination is configured — and unlike every other missing setting, an unset destination does not stop the system starting.
Consequence

R6 cannot be marked partially done and moved past. Per-property approval is non-functional end to end until both sides resolve the same approver. That is a blocker, not a caveat — see NEW-4.

3Principles

Four. Each is testable, and each has at least one acceptance criterion that exists solely to defend it.

P1 — A per-property approver, no master key

A key that approves one property fails on another. A property with a broken approver entry refuses rather than falling back to a wider identity. Defended by AC-B6.1, AC-B6.3.

P2 — Nothing fails open

A check that cannot run reports failure. Missing configuration refuses; it does not proceed quietly. Defended by AC-B8.1, AC-B8.2, AC-B8.3.

P3 — One project, one domain, one website

A design reaches only its own project's CMS. A second website is refused or lands separately — never a silent overwrite. Defended by AC-A2.1, AC-A2.2, AC-A2.3.

P4 — One publisher

MMS-CMS is the sole publisher of platform sites. Design creates; the CMS publishes; nothing else reaches the public. Defended by AC-A2.3, AC-B9.2.

4Requirements

Numbering follows the brief so the mapping is obvious. Requirements marked new are additions — each says why it is here and what breaks without it.

Phase 0 — Close the surface

Promoted from the brief's last group to first: every requirement after it assumes an authenticated admin. Building the levels and roles on an open control plane means building them twice.

Outcome
Every administrative action requires a signed-in administrator. An unauthenticated request to any admin action is refused.
Why
Today the admin surface is reachable on the public address with no sign-in at all — including deleting a project and minting a machine key. The brief's honest-list item 7.
Acceptance
AC-D14.1 — an unauthenticated request to any admin or operator action is refused; the console requires sign-in.
Depends on
Nothing. This is the first thing.
Note
The password hashing, signed-session and invite primitives it needs already exist elsewhere in the system and should be reused, not rewritten.
NEW-1The admin surface reveals no secret it does not have tonewPhase 0not started
Outcome
No administrative response returns a usable credential. An existing machine key is never returned in plaintext after minting, and a project listing returns neither a working invite link nor a live capacity token.
Why

Outcome
An Operator owns many Businesses; a Business owns many Projects. Each level resolves its children and the chain is queryable. Every stored record carries its full address, so a query that does not name one returns nothing.
Why
The single largest gap. Today's project is exactly the target's project — the two levels above it do not exist at any layer, so the platform cannot be sold to an agency.

Phase 4 — Governance, with proof

NEW-4The issuing side must resolve per-property approvers toonewPhase 4blocker
Outcome
The side that issues approvals and the side that checks them resolve the same approver for the same property. Neither has a privileged identity the other does not recognise.
Why
The reason R6 is blocked rather than merely incomplete. The issuing side verifies every approval against a single platform-wide identity, so a property-signed approval is refused at issue time and the checking side's per-property support never comes into play. AC-B6.1 fails on day one without this.
Acceptance
NEW-4a — register a property-specific approver, then obtain an approval for that property from the issuing side: it is issued, and the checking side accepts it. Today this fails at the first step.
Depends on
R1
Note
This is the first thing in Phase 4.
R6Per-property approver: registration, delegation, rotationPhase 4blocked
Outcome
An approver is registered per property and resolved by walking up Project → Business → Operator where delegation is configured. A property's approver approves only that property. Registration, rotation and revocation are first-class, and a rotated-out identity stops being accepted immediately.
Why
The platform key is the pilot arrangement only. An agency cannot be sold a product in which the platform holds the only signature that authorises changes to its customers' sites.
Acceptance
AC-B6.1 — P's approver accepted; another property's approver refused for the identical action. AC-B6.2 — after rotation, the old identity is refused and the new one accepted. AC-B6.3 — no single identity satisfies two properties' approvals. AC-B6.4 — a Business approver covers its own projects when configured, never another Business's.
Depends on
R1, NEW-4
R7Import and publish each gated, bound, and gated separatelyPhase 4partial
Outcome
Import and publish each refuse without a valid approval bound to the exact artefact — unexpired, unspent, single-use. One approval never covers both, and rows can be inspected between the two gates. Enforcement is at the server, so holding valid machine credentials does not bypass it.
Why
The whole "with proof" claim rests on this. An approval that can be replayed, reused across artefacts, or spent on a different action is not an approval.
Acceptance
AC-B7.1 no approval: refused, nothing imported. AC-B7.2 wrong artefact: refused. AC-B7.3 expired: refused. AC-B7.4 already spent: refused. AC-B7.5 one approval cannot cover both; rows inspectable between them. AC-B7.6 all of the above still refused when the caller holds valid machine credentials.

Note
The gate exists across eight actions, binds to the artefact, expires, is single-use, and spends the approval before acting. Missing: per-property resolution, and a guarantee that a property currently exempted from the gate cannot stay exempt in production.
R8Fail-closed everywherePhase 4partial
Outcome
No check may fail open. If a checker crashes the action is blocked, and the blocked result is distinguishable from a success. If the approval policy is missing or unreadable, every gated action refuses. A check that cannot run reports failure, never a zero-findings pass.
Why
Principle P2. Today the importability check passes the share through unchecked when it crashes — honest-list item 3 — so a crash looks like a success. That is the most dangerous shape a bug can take.
Acceptance
AC-B8.1 — fault-inject a crash into the importability check, then share: blocked, and distinguishably so. Going through unchecked is a FAIL. AC-B8.2 — policy missing or unreadable: every gated action refuses. AC-B8.3 — a check forced not to run yields failure, never a zero-findings pass.
Depends on
R7
Note
The approval policy already fails closed correctly. The importability check does not, and the pre-flight does not block at all (R11).
R9The proof chain: receipt, live verification, known-good, immutabilityPhase 4not started
Outcome
Every publish produces an immutable receipt naming the approved content's identity, the deploy identity, the live-verification result, the timestamp, the previous known-good reference — and the build that performed it. Verification fetches the deployed site and confirms served content. A known-good bundle is retained before every push and is retrievable. Receipts cannot be edited or deleted.
Why
Without this, "it went live" is an assertion. Today a deploy is marked live purely because the deploy tool exited cleanly, and nothing has ever fetched the result. The incident that motivated this — a site that went live essentially unstyled — was caught by a person looking at it, which is exactly the dependency this removes.
Acceptance
AC-B9.1 — a receipt per publish with every named field present. AC-B9.2 — verification fetches the deployed site and confirms served content; a deliberately missing route serving a fallback is caught as FAIL. An HTTP-200 check is not sufficient. AC-B9.3 — a known-good bundle retained before each push and retrievable for reconstruction. AC-B9.4 — editing or deleting a past receipt or approval record is denied.
Depends on
R7
Note
Further from done than the brief implies — none of receipt, live verification, known-good retention or rollback exists on the platform's publish path. Two mitigations: the approval store is already append-only and immutable by construction, which satisfies B9.4's shape; and the studio's own deploy path already polls until reachable and keeps a richer record — adopt both. Note also that the current publish wipes the previous generation at the start of each publish, so retention must exist before B9.3 is possible at all.

Acceptance
AC-B10.1 — verification succeeds with the issuer offline, using unshared code. AC-B10.2 — a tampered approval fails on the acting side regardless of the issuer's record; both sides pass the shared suite.

6The brief's open questions, answered

The brief asks the PRD to resolve five. Here they are, with reasoning.

6.1 Do the two publishers converge?

Answer

Yes — one publisher. MMS-CMS remains the sole publisher of platform sites, and the platform's deploy path adopts the studio path's deploy record and live-reachability verifier.

The finding that decides it: the studio already has a complete, independent deploy path of its own, and it is better at proof than the platform's. It keeps the provider's deploy identity, a reachability timestamp, a status message and the target, and it polls the deployed address until it is actually reachable before calling a deploy done. The platform's own path records none of that and marks a deploy live on the deploy tool's exit code.

So convergence is not "retire one and rebuild the other". It is: keep one publisher — the CMS — and move the studio path's proof mechanisms into it. That satisfies AC-B9.1 and AC-B9.2 with code that exists and is tested, rather than writing a second verifier.

What it costs. The two paths share nothing today — different credential stores, transports, record shapes and status vocabularies, and neither can see the other's deploys. The adoption is real work, but smaller than building live verification from nothing, and it removes a class of "which publisher did this site go through?" ambiguity. Studio-built sites deploying themselves today are outside the proof chain until they migrate, which is part of Phase 4 and should be said plainly rather than implied away.

6.2 Where do governance records live?

The issuing side is already the authoritative store, and receipts join it there. It is already append-only and immutable by construction — not by the absence of an edit route but by the store itself refusing edits — which is exactly the property AC-B9.4 tests. Receipts added there inherit that immutability rather than needing their own.

The acting side keeps its own independent ledger of what it spent and what happened, because R10 requires the two ends not to depend on each other. The two records are reconciled, not merged.

A portal projection, if one is built, is read-only, addressed by the full hierarchy so R5's scoped visibility applies to it, and explicitly derived — the projection is never the source of truth, so a disagreement resolves in favour of the store.

6.3 Approver registration, delegation and rotation

  • Registration attaches an approver to a property with an effective-from stamp. The registry is the only place this mapping lives, and both ends read the same registry — that is NEW-4, and nothing else in R6 works until it is true.
  • Delegation is explicit, never implied. A Business approver covers its own projects only when configured to, and never another Business's. A property with a broken entry refuses rather than falling back up the chain — a fallback that widens scope on error is a master key by another name.
  • Rotation takes effect immediately: approvals signed by the retired identity stop being accepted the moment the new one is registered. History is retained so an old receipt can still be explained, but a retired identity never authorises anything new.
  • Revocation without a replacement leaves the property with no approver, and every gated action there refuses. That is the correct failure, and it is what AC-B8.2 tests in the small.

6.4 Staging self-service for the studio

A studio provisions its own staging project through the same path that creates any project, with the machine door as the caller — which is already how a new site is created today. What is missing is not the creation but the loop: pre-flight, import under approval, inspect, publish under a second approval, all driven from the studio without a developer holding the credentials.

Two practical requirements fall out: the staging project must be gated exactly like a production one, so the loop being exercised is the real one — a staging project exempted from the approval gate proves nothing; and the pre-flight must block (R11), because a self-service loop with a non-blocking check will push a broken bundle at machine speed.

6.5 A correction the PRD should not inherit

The "no CSS" bundle was v4, not v7

The brief describes the no-CSS bundle as the v7 case. It was v4 — eight of 617 style rules survived the publish step, so the site went live essentially unstyled. v7 was the recovery build and reached 600 of 666. The mislabel came from a working note and has propagated.

This matters because the pre-flight threshold in R11 is being specified against that incident. Specifying it against the wrong build would set the threshold against a bundle that was fine.

How the suite is run

Unchanged from the acceptance document: each criterion produces evidence — the exact request, the raw result, and a PASS or FAIL. It runs on a throwaway or staging project, never on a live site. It is run by someone other than the builder. "Refused" always means the server refuses, re-tested with valid credentials so a credential holder cannot bypass it.

Non-goals

  • Route B — several websites inside a single project. Route A is the path: a project stays the unit of isolation and the levels are added above it. Unless the owner decides otherwise.
  • Anything that relaxes P1, P2, P3 or P4.
  • Rebuilding what already works — per-project isolation, the design-to-CMS handover, the CMS's role and capability system, and the atomic publish swap are extended, not replaced.
