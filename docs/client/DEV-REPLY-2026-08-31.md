## 2. Fixed: per-row SEO now renders on `pages`

Your diagnosis of the *symptom* was exact — pages carried no SEO into `<head>`.
Your question was whether passing the row's cells is the whole fix or whether
the snapshot lacks them. **The snapshot lacks them**, so it was not a one-liner:

`SiteDocument.pages[]` is a page *tree* — `id, slug, title, nodes, template`.
The `pages` row's `seoTitle` / `canonicalUrl` / `jsonLd` cells are dropped when
the row becomes a page tree, so there was nothing at the render site to pass.

What changed:

- `documentSeoFromCells(cells)` — one exported mapper, now the single definition
  of which cells become which tags. Both render paths use it, so entries and
  pages can no longer drift apart the way they just did.
- `renderMergedTemplate` takes an optional `seo` override and forwards it to
  `publishPage`.
- The page path reads its own row and passes the result. This covers the static
  bake, the live fallback and republish in one place, because all three route
  through the same function.
- The 404 path deliberately does **not** get it: a 404 body is served at
  whatever URL missed, so a canonical resolved from the template row would point
  a crawler at the error page as though it were a real document.

Verified: `bun test src/__tests__/publisher/documentSeoHead.test.ts` → 9 pass.
That file is new; there was no test over the SEO head before, which is how pages
stayed broken while entries worked. It pins canonical, `og:`, JSON-LD, the
`<` escaping inside the JSON-LD block, unsafe-URL rejection, and the
entry-stack path, so this cannot regress silently again.

Full typecheck (`tsc --noEmit`) is clean.

**Not done, and deliberately:** `canonicalUrl` / `ogTitle` / `ogDescription` /
`ogImage` / `jsonLd` are still added to `pages` by `connector_add_seo_fields`
rather than shipped as built-in columns. Making them built-in means a JSON-array
migration over `fields_json` in both Postgres and SQLite against live installs,
and the append-if-absent form is fragile enough in SQLite that we are not
willing to run it blind on your data. **Answering your §6 directly: yes, ship
the `pages` table in your bundle with the SEO fields appended — that is the
supported path, and `connector_add_seo_fields` does the same thing.** Once the
fields exist, the renderer now honours them.

## 3. Fixed: your bundle can no longer import into nowhere silently

You reported that `connector_preview_import` accepts cells for fields that do
not exist on the table and still reports a clean preview. Confirmed — the
preview only diffed row ids and slugs and never looked at cells.

Preview now returns `unknownFields`: `{ tableId, tableName, fieldId, rowCount }`
per field the destination table does not define, ordered by how many rows carry
it. Empty on a clean bundle.

It compares against the **destination** table's schema when the table already
exists locally, because that is the schema the import will actually write
against. This is the check that would have caught your `canonicalUrl` / `jsonLd`
probe, and it is the same failure shape as the stored-but-never-rendered SEO bug
— which is why it was worth fixing rather than documenting.

## 4. Fixed: `connector_export_manifest` no longer kills the session

Confirmed exactly as you described: the tool took only `target` and returned
every row with full cells. 398 page rows is tens of megabytes in one response.

It now takes the same shape as the `list_rows` fix you already have:

- `rows`: `summary` (default) · `none` · `full`
- `tableId` — restrict rows to one table
- `limit` (default 200, max 1000) / `offset`

`summary` drops row cells and returns `id, tableId, slug, status, title` plus
`cellKeys`, which is enough to diff two sites without moving the bodies.
`none` keeps tables and counts only. Every response carries `counts` and
`rowsTruncated`, so a narrowed manifest can never be misread as a complete one.

## 5. Fixed: `publish.headers` is gone, not just dead

You were right, and you lost work to it. Rather than leave a declaration that
does nothing, we removed it from the SDK types and the docs.

It was also never implementable as designed: published sites go out as static
Cloudflare Pages uploads, which serve response headers from a `_headers` file in
the deployed directory, not from the CMS process. A header set inside the publish
pipeline could not reach a visitor even if the filter had been wired.

`publish.html` is real and stays — it runs once at the dispatcher for every
HTML-emitting path, including the static bake. Your reading of it was correct.

**Response headers are the deploy step's job now.** See §6.

## 6. Fixed: robots.txt, `_headers` and llms.txt — and noindex is the default

This is your §1/§6 from round 2 and round 3, and it is the answer to "can the
control plane emit root files": **yes, and it now does.**

The deployer writes all three into the upload directory before
`wrangler pages deploy`, on every deploy — the deploy dir is a publish slot that
the CMS wipes and rebuilds, so writing each time is what keeps them present.
The placeholder deploy for a brand-new tenant gets them too, so the first thing
a crawler can find on a fresh tenant URL is already guarded.

Which pair gets written is driven by a new `search_indexing` column on the
tenant, **defaulting to false**:

- indexing off → `robots.txt` with `Disallow: /`, `_headers` with
  `X-Robots-Tag: noindex, nofollow`, and an `llms.txt` saying do not index,
  crawl or train.
- indexing on → permissive `robots.txt` (with a `Sitemap:` line when we know the
  domain), and the `_headers` noindex block is actively removed so a stale one
  cannot keep a site out of the index it was just opened to.

Existing tenants backfill to `false`. A live site that *should* be indexed gets
the flag set once, on purpose. That inverts the default you were arguing against
— exposure is now a deliberate act.

**This makes your noindex plugin unnecessary.** It also gives you the reliable
header path you asked about, at the layer that can actually deliver it.
