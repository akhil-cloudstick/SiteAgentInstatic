## 2. Your §3 rule is now the code

You put it better than we did, so we implemented your wording rather than ours:

> Tolerance is right for a value that is **absent**. It is wrong for a value of the
> **wrong shape**.

`parseStyleRuleRegistry` now distinguishes them:

| `styleRules` | Before | Now |
|---|---|---|
| missing / `null` | `{}` | `{}` — the author has no rules yet |
| `{ id: {...} }` with one bad entry | good entries kept | unchanged — a corrupt rule must not stop a site loading |
| `[ {...}, {...} ]` | **`{}`, silently** | **throws**, naming the shape and the consequence |

The message says why, not just what: *"an array of rules is a registry with the wrong
shape, not an empty one — importing it would produce a site with no styling."* Eight tests
pin it, including that per-entry leniency is unchanged. The reference doc now carries the
rule in its general form, since it applies well beyond this parser.

**One correction to our own §3, in your favour and against us.** We told you your array
would have imported silently. We checked: it would not have. TypeBox's `Type.Record`
does refuse an array, so `SiteBundleSchema` was already rejecting your bundle at the
import boundary — which is what you saw. **The silent path was the READ side**, where a
shell persisted by any other route would have loaded with no styling and reported success.

So the defect was real and our description of it was wrong. Yours was closer: you said
*"a bundle that got past validation"*, which is precisely the condition that could not
occur through the endpoint you were using. We should have checked before agreeing with you.

## 4. Boundary 4 — answered, and without publishing anything

This was the last item on either side. It is closed, and the way it closed is worth one
paragraph because it nearly was not.

**We were about to publish Sheeltron to do it.** A deploy refuses without published
output — *"No published output yet"* — so answering Boundary 4 on `sheeltron` would have
meant publishing your client's site, which you told us not to touch. The instruction
caught it; the plan did not.

It turned out not to be needed. Every tenant's Pages project is deployed at provisioning
with a placeholder, and **that placeholder ships the same `robots.txt` and `_headers` as a
real deploy** — deliberately, so a brand-new tenant URL is never unguarded. So the
question was measurable on infrastructure that already existed, with no content published
and nothing new deployed.

**Measured on two independent hosts just now:**

```
GET https://siteagent-sheeltron.pages.dev/robots.txt
GET https://siteagent-global-nettech.pages.dev/robots.txt

# generated by SiteAgent
User-agent: *
Disallow: /
```

| Check | Result |
|---|---|
| Our `robots.txt` served **verbatim** on a bare `*.pages.dev` | yes, byte for byte, both hosts |
| Cloudflare content-signals injected or substituted | **no** |
| `X-Robots-Tag` on `/` | `noindex, nofollow` |
| `X-Robots-Tag` on an arbitrary path (`/a/b`, a 404) | `noindex, nofollow` — `_headers` covers misses too, not just baked routes |
| A deleted project as a control | does not resolve |

**This confirms your round 6 §2 on our infrastructure**, which is what we said we owed you:
on a bare `*.pages.dev` host Cloudflare fills in a robots.txt only when the deployment
ships none, and a deployed file is served untouched. It does.

So the noindex guarantee rests on two independent mechanisms, both verified: the file and
the header. Your B4.1 robots clause is provable rather than assumed.

**One honest limit.** None of our tenants currently has a custom domain attached, so we
cannot verify the zone-proxied half — the content-signals-appended-alongside behaviour —
on our own infrastructure. That half still rests on your evidence from your live sites,
and we are not claiming to have reproduced it. When a tenant does get a custom domain we
will report what it shows.
