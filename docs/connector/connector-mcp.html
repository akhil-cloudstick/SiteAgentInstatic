Connector MCP Guide

How to run the connector, how a remote client reaches it over Tailscale, and — just as important — what it deliberately will not let you do.

s:\SiteAgentHub\Connector Bun 1.3.x POST /mcp Bearer
01

What this is

The connector migrates a site into Instatic CMS: posts become a managed collection rather than hundreds of flat pages, shared chrome becomes reusable components, and one template wraps every post. The MCP server is the remote control surface for that tooling — it lets someone drive the connector from Claude or any MCP client without shell access to this machine.

Read this before planning around it

MCP is not the migration transport, and that is a design decision rather than an unfinished feature.

Instatic's own publish tool accepts an empty input schema and no expected hash, and its content writes relay through an open browser tab. Driving a release through that surface would reintroduce the approval race the design spent six review passes closing — a release could publish something other than what was approved, and nothing would notice.

So the release path stays in the CLI, behind the approval bindings and the server-side expected-hash contract. This MCP server exposes read-only and gate tools only. It can tell you whether a release is safe; it cannot perform one.

02

Running it locally

Generate a token first. It is read from the environment and never from a file in the repo or a command-line argument — arguments land in shell history and in the process list on a shared machine.

# 1. generate a token
bun -e "console.log(crypto.randomUUID()+crypto.randomUUID())"

# 2. prove the conversion environment works before anything else
cd s:\SiteAgentHub\Connector
bun src/main.ts doctor

# 3. start the MCP server
export MMS_CONNECTOR_MCP_TOKEN=<the token>
bun src/main.ts serve --port 8787

It binds to 127.0.0.1 by default. That is intentional: remote access arrives through Tailscale, which routes to the loopback listener, whereas binding 0.0.0.0 would additionally expose the port to anything else that can reach the machine.

Check it with curl http://127.0.0.1:8787/health — you should get {"ok":true,"service":"mms-connector-mcp"}.

03

Remote access over Tailscale

Tailscale Funnel permits only three ports — 443, 8443 and 10000 — and the Operator control plane already claims two of them. It opens its own funnel on boot and closes it on shutdown (GATEWAY_FUNNEL=0 to manage by hand), so this is not a blank slate.

PortCurrentlyOrigin
443Operator gateway — reverse-proxies operator, every tenant's OpenDesign and Instatichttps://siteagent.tailbbb0d2.ts.net
10000Tenant test funnel — one tenant editor published for remote access…ts.net:10000
8443Free — the only spare…ts.net:8443
Correction — do not use the bare gateway origin

The gateway origin routes to the control plane, not to this server.

https://siteagent.tailbbb0d2.ts.net is port 443, which the Operator control plane owns and reverse-proxies to per-tenant backends. Pointing a client there for MCP gets the control plane, not the connector. The port must be in the URL.

Option A — take the spare port. Nothing in Operator changes, and it works immediately. It does spend the last free funnel port.

tailscale funnel --bg --https=8443 http://127.0.0.1:8787

# public URL
https://siteagent.tailbbb0d2.ts.net:8443/mcp
export MMS_CONNECTOR_ALLOWED_ORIGINS=https://siteagent.tailbbb0d2.ts.net:8443

Option B — behind the existing gateway. Matches the "one funnel fronts everything" design and keeps 8443 spare, but needs a proxy route added to the control plane, so it is a change to Operator rather than pure configuration.

# route /connector-mcp -> http://127.0.0.1:8787/mcp in the control-plane proxy
https://siteagent.tailbbb0d2.ts.net/connector-mcp
export MMS_CONNECTOR_ALLOWED_ORIGINS=https://siteagent.tailbbb0d2.ts.net
The trap that already bit this repo once

The funnel rewrites Origin and Host, so the server rejects every request until you tell it the public origin.

Instatic's CSRF check hit exactly this, and Operator/pending.md records the workaround. Our server needs the same thing said explicitly:

export MMS_CONNECTOR_ALLOWED_ORIGINS=<the origin from the option you chose>

A request with no Origin header is allowed — that is a CLI or server-to-server caller, and it cannot be a browser rebinding attack because browsers always send Origin cross-origin. A request with a wrong Origin gets 403 before the token is ever compared.

04

Connecting a client

Give the client the public URL and the token. Nothing else — no repo access, no credentials for the CMS.

claude mcp add --transport http mms-connector \
  https://siteagent.tailbbb0d2.ts.net:8443/mcp \
  --header "Authorization: Bearer <token>"

Or, for any MCP client that reads JSON config:

{
  "mcpServers": {
    "mms-connector": {
      "type": "http",
      "url": "https://siteagent.tailbbb0d2.ts.net:8443/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}

Tools available today

Only tools whose implementation exists are registered. A tool that advertises itself and then returns "not implemented" is worse than an absent one — an agent will plan a whole migration around it and fail halfway.

06

Security posture

  • Refuses to start unauthenticatedA missing or under-32-character token aborts before the port opens. A server that starts and then rejects everything looks like a network fault and wastes an afternoon.
  • Constant-time token compareSo a wrong token cannot be recovered by timing the response.
  • Origin checked before authA rebinding attempt is rejected without the token ever being compared.
  • Loopback bind by defaultTailscale routes to loopback. Exposing 0.0.0.0 has to be asked for explicitly.
  • No CMS credentials hereThis server exposes migration tooling, not content. It holds no session for any Instatic instance.
  • One shared secret per deploymentDeliberately not a user system. Rotate by restarting with a new token; there is no revocation list to drift out of sync.
07

What is not built yet

Being straight about this matters more than the feature list, because the gap is where a client's expectations will land.

Nothing here talks to a CMS yet. There is no login, no session handling, no import and no publish. The bundle emitter that converts a real site does not exist — doctor converts a fixture, not your content. The Instatic If-Match changes that close the release race are specified but not written.

What is proven is the foundation the rest stands on: a separate package can reuse Instatic's own converter rather than reimplementing it, and the hashing and approval machinery agrees with the server byte-for-byte. That was the make-or-break question, and it is answered.

Do not promiseA working migration, a preview against a live tenant, or a release. None of those paths exist yet. This server is a control surface over the parts that do.
