The verdict I accept: the plugin-based activation design was wrong, and the plan promised guarantees the chosen APIs cannot deliver. Everything moved into the CLI, the plugin became optional, and the promises that could not be kept were removed rather than softened.

The second review pass closed six more. Two of those were not gaps in detail — they were claims that could never have been true: a rerun that writes nothing while unconditionally publishing the site, and a backup that does not restore what it says it restores. Both are corrected below rather than reworded.

02

Two promises that were false

Corrected

A SiteBundle export is not a rollback backup.

The plan said: take a full export, checksum it, restore-drill it, and you have a safety net. The export carries the site shell, tables, rows, media, folders and redirects — and nothing else. No version history, no active-version pointers, no published site snapshot, no baked artefacts on disk, no plugin state or grants, no users, roles or audit.

Restoring it gives the draft content back and leaves the published state wrong. That is worse than no backup, because someone would trust it. A real pre-write backup is a database dump plus the uploads directory, taken together with the target quiesced — that is what gets checksummed and drilled. And for a first migration the actual rollback is a traffic switch, not a restore at all.

Corrected

Full-site publish always writes, so the rerun could never have been a no-op.

The idempotency gate promised "zero publish calls, zero new versions" on a second run. But the release command called full-site publish unconditionally, and that path creates page versions every single time. The gate was unpassable as written.

Full-site publish is now conditional: skipped when the draft hashes identically to what sits behind the current published snapshot. The comparison covers the site document, not just the shell — an earlier draft said "shell", which would have skipped exactly the publishes that matter, since the shell holds breakpoints, settings, style rules and runtime but not pages, templates or components.

But the hash must exclude saved layouts, and an earlier draft explicitly included them. Verified in our fork: the draft-document assembler returns shell, pages and visual components, then sets layouts: [] with the comment "Saved layouts are editor-only; publishing ignores them." Including layouts flips the hash on a layout edit and triggers a full-site publish that changes nothing published — the exact false positive this conditional exists to prevent. The hash mirrors what the assembler actually returns, not what the phrase "site document" suggests.

The gate is restated to include "zero new page versions because the publish was skipped", with the skip decision logged either way. If the shell genuinely changed, the run is not a no-op and does not claim to be.

03

The correction that simplifies everything

Verified in our fork

A core row-publish endpoint already exists. The activation plugin is deleted.

POST {prefix}/data/rows/:id/publish
  → publishDataRow(db, rowId, user.id, options.uploadsDir)

Revision 1 argued the plugin API was the only headless door to activation. It is not. The core HTTP route does the same job through the ordinary CMS session — and it passes uploadsDir, which the plugin path does not, so it also bakes the row artefact. The plugin was strictly worse and added install, permission, sandbox and route failure points for no benefit.

Deleting it collapses three arms into one: the CLI owns the whole pipeline. The plugin survives only as an optional extra for site packs and CDN URL rewriting.

Still true — and now handled properly

Imported rows have no active version, so they do not render.

Import writes data_rows and nothing else. Public routes join through active_version_id. But there are two gaps, not one: new rows render nothing, and a merge-overwrite of an already published row keeps its old active version — so visitors see stale content rather than no content, which is harder to notice.

Fixing it needs two publish calls, not one: a full-site publish for the site snapshot and page versions, then per-row publish for the entries. The full-site publish requires pages.publish and a step-up authentication challenge. Revision 1 had neither.

04

What goes in, and what runs when

Corrected

The input is an approved immutable archive, not a live recrawl.

Revision 1 described the input as "an HTML export, with an optional structured feed". That is wrong, and the consequence is not cosmetic: a pipeline that re-reads a live site cannot tell you what it published, because the thing it published no longer exists in the form it was approved in.

The connector takes a content-addressed archive reference with a snapshot hash and a verified manifest — not a URL. It records that hash in its run manifest and refuses to release against an archive whose hash does not match the approval it was handed. Re-capturing the source is a separate upstream action that produces a new artefact and re-enters approval; it never silently becomes the next run's input.

Corrected

Two commands, not one. Staging and releasing are different actions.

push-draft                     preview + import, never publishes; emits a draft hash

release --approval <id>          the approval record itself
        --signers  <ids>         who signed it
        --snapshot <hash>        the source archive it was granted against
        --document <hash>        shell + pages + visualComponents — LAYOUTS EXCLUDED
        --rows     <digest>      every approved row's canonical content hash
        --media    <digest>      byte-level hash of every approved media asset
        --contract <hash>        the four system tables and their field schema
        --recipe   <hash>        connector version + config + strategy + flags
        --manifest <id#hash> manifest identity, version AND content hash
        --project  <id>          the exact project
        --domain   <fqdn>        the exact domain
        --target   <host>        the exact tenant

Revision 1 fused import and activation into a single command. That is what made it both unreviewable — nobody could inspect the result before it went live — and unrecoverable, because there was no point at which anyone had agreed to what was about to be published.

Revision 2 bound only the source snapshot, which is not enough: you could approve draft A on target X and release draft B onto target Y, and every check would still pass. Every value must match the approval record.

The document hash alone is not enough. The document covers the site with its pages, templates and visual components — layouts excluded, as above — and it does not cover the 397 post rows. Binding only the document would let every post body change between approval and release with the check still passing. The row digest closes that half, and the media digest closes a third: rows can reference media whose bytes changed while ids and cell values stayed identical, so that hash is byte-level, not id-level. The contract hash covers the four system table definitions — if a field is added, renamed or retyped after approval, the emitted rows no longer mean what was approved, so the release fails rather than writing cells against a shifted schema.

An approval is a statement about one specific draft on one specific target. The command must be incapable of reading it as anything looser.

Open — no clean fix available today

The hash check is a race, and re-checking does not close it.

A client-side check is time-of-check-to-time-of-use. The CLI reads the draft, hashes it, compares, then calls publish — and an editor session can change content inside that window. Nothing the CLI does alone fixes this. Hashing again immediately before the call narrows the window; it does not close it, and a plan claiming otherwise is claiming a guarantee it cannot provide.

Two things actually close it, and both are prerequisites rather than implementation details:

Server-side expected-hash — and the two endpoints need different placement. An earlier draft said "inside the same transaction that reads the draft" for both. That is wrong for the site path and would have been costly to discover.

Site: the publisher deliberately reads the draft outside its database transaction, because dependency installs and per-page esbuild runs take seconds and the SQLite adapter serialises every transaction through one chain — doing that work inside would stall every concurrent autosave and row publish. So the contract is: flush collaboration, take the existing publish lock, assemble the document once, compare If-Match against it, and then reuse that exact captured object for every subsequent build and write. No long site transaction is needed, and the publisher must not reread the draft afterwards.

Row: compare inside the existing row transaction, immediately after the reread and before version-number allocation, version insert, row update, redirect creation, audit, content event, artefact write or cache bump.

Both return 412 Precondition Failed with a stable error code and write nothing — no snapshot, version, audit, artefact, hook, cache bump or webhook. One If-Match contract, not a second body-plus-409 variant. The good news: the canonical hash function already exists — siteContentHash over sorted-key canonical JSON — so this reuses core machinery rather than inventing a parallel scheme.

Or an enforced write freeze. The target rejects draft writes for the release window, with editor sessions disconnected rather than merely asked to stop. An advisory "please don't edit" is not a freeze.

Until one exists, client-side rehashing is diagnosis only. It narrows the window, it does not close it, and it does not authorize a production release. The only acceptable v1 alternative is a genuine server-enforced writer freeze — proxy-level, returning 423 Locked to every principal except the connector, with editor sessions, tokens, schedulers, plugin mutations and collaboration writes all revoked and canary-proved, recorded in a hashed freeze-proof inventory. An operator message asking people not to edit is not a freeze.

07

The one disagreement

Settled — was a disagreement

The route prefix and cookie path differ from public upstream — now confirmed by both sides.

Instatic/server/handlers/cms/shared.ts:24
export const CMS_API_PREFIX = '/cms/api/cms'

The review originally reported /admin/api/cms from public upstream. It has since inspected the fork source directly and confirms /cms/api/cms — the dispute is settled and should not be reopened. One addition: the prefix and the session cookie path are a single compatibility unit. Our fork sets Path=/cms, so a connector that gets the prefix right and the cookie path wrong still fails.

The useful conclusion is that neither of us should hardcode it. The connector imports the prefix constant from source and, when addressing a host it did not build, probes the prefix at startup and fails loudly on mismatch. A disagreement becomes a compatibility lock — which also catches the next divergence, and there will be one.

One further claim could not be checked: the review cites DECISIONS.md as a governance stop on implementation. There is no such file anywhere in this repository. If that approval process governs this work it is a genuine input, but it is a process fact rather than a code fact — an external gate, not a repository constraint.

08

Decisions required before any code

Each one gates a promise the plan would otherwise make falsely. None can be deferred into implementation.

A

How redirects get imported

The chosen import strategy cannot carry them. Until this is settled, redirect parity is not a gate the connector can pass — and it was one of the headline deliverables.

Note that replace is green-target-only. It deletes every row, every non-system table, all media folders and all redirects before reinserting. On a target holding live content that is not a strategy, it is a wipe. The connector must refuse it unless the target is verified empty of user content, checked before step-up rather than after. It is an option for a first migration onto a fresh target and for nothing else.

replace — green target only narrow core redirect endpoint import at the edge
B

Whether per-entry SEO waits for a core change

The publish filter cannot see which post it is rendering. Native title and description already work and ship regardless. Canonical, Open Graph and Article JSON-LD need the filter context to carry the URL path, table and entry id.

ship native SEO now, extend core later make the core change part of this work
C

How the site serves root sitemap and robots

Plugin routes mount under a runtime path and cannot claim the host root. A sitemap served from a nested path does not cover the site, and robots must sit at the root to be read at all.

core root route edge rewrite
D

Blue-green or in-place

Nothing in this pipeline is atomic. For a first migration, publish to a separate target, verify completely, then switch traffic. In-place means old and new row versions coexist during the release window, so templates must stay backward-compatible throughout.

blue-green (recommended for first run) in-place with compatibility plan

11

Operational gates

Five areas the plan left implicit. Each is a decision with a stated default, not an open question — leaving them unwritten is how a migration tool quietly becomes an owner-account script with credentials in a config file.

  • GovernanceAn approval record names the source snapshot, draft hash, Binding Manifest, target, signer and time. Written before release, immutable after. Without a stored record there is nothing for release to verify against.
  • PermissionsA dedicated service account, never an owner account. The normal floor is six rights — site-read, export, import, structure-edit, page-publish, publish-any. I said four, then five; both were wrong. Site-read is needed to read the draft document and hash it, without which the approval binding does not work, and structure-edit is every migration that ships a shell, not an edge case. Content-manage is added only for a replace run, and content-edit-any only for a prune run — the status endpoint takes data-editor rights, and content-edit-own cannot reach author-stripped imported rows. Both granted per run and revoked after.
  • SecretsCredentials from the environment or an OS keychain. Never a config file in the repo, never a CLI argument — arguments land in shell history and process listings. Session cookies stay in memory and are discarded; manifests and logs redact them.
  • DeletionRows on the target but not in the source are left untouched and accumulate silently. They are reported every run and never removed implicitly. Pruning is an explicit approved pass that unpublishes rather than hard-deletes, so the route stops resolving without destroying history.
  • SEO acceptanceNative title and description ship and are gated on exactly one of each per route, non-empty, matching the source. Canonical, Open Graph and JSON-LD are out of scope until the core filter context carries the entry and URL — no partial version via slug-guessing.
  • EscalationThe rights granted temporarily are content-manage for a replace run and content-edit-any for a prune run. Both revoked immediately after, rather than left in place.
  • Live authentication proofEvery auth claim here — login, MFA, step-up, cookie rotation, the no-Origin CSRF path — comes from reading code, not from running it. None is proven against a live instance. That proof is a prerequisite, because a scripted release that discovers its auth assumptions are wrong discovers it mid-migration.
  • Plugin HTML hookspublish.before and publish.after run inside the HTML pipeline, so they fire per rendered page or row artefact — not once per publish operation. Inventory every side-effectful listener and suppress it for the release window, then restore.
  • Deploy webhook — separate mechanism, and mis-sequencedOur fork POSTs INSTATIC_DEPLOY_WEBHOOK from the full-publish handler, fire-and-forget, unawaited. It is not a plugin hook and needs its own rule. Worse, it fires after full-site publish and therefore before the row batch — it would deploy a site whose 397 posts are not yet activated. Suppress it for the whole window; deploy once, explicitly, after CMS state and public routes verify, carrying a release id and returning a terminal status. A fire-and-forget POST cannot be a release-completion signal: CMS publish success does not prove deploy success.
12

Idempotency, as a mechanism

Revision 1 asserted that a second run would be a no-op. It would not have been — the import upserts every supplied row and every publish inserts a new version. Stable ids alone do not achieve this. What does:

  • Canonicalize, then hashExclude volatile timestamps and object key order before hashing each logical row.
  • Keep a run manifestSource key, row id, content hash, last version id, public path.
  • Compare before importingAgainst target state or the last verified manifest.
  • Omit unchanged rowsLeave them out of the bundle entirely where it is safe to do so.
  • Publish selectivelyOnly rows whose content differs, or which have no active version at all.
  • Decide deletion policyA merge import leaves target-only rows in place. That is a choice, so make it one.
  • Resume re-reads target stateNever trust the local cursor alone after a failure.
  • Record the live hash lastOnly after route verification passes, never before.
Second-run gateZero changed rows, zero row publishes, zero new row versions, zero new page versions because the full-site publish was skipped, and identical public response hashes once volatile headers are normalized. The skip decision is logged either way.
13

Verification

A connector-owned integration suite against a scratch instance. The existing round-trip test proves row, table and strategy behaviour only — it does not prove rendering, redirects, or idempotency, and revision 1 leaned on it as though it did.

  1. Fork compatibility — prefix, schemas, permissions, version and commit match the lock file
  2. Doctor — environment loaded, expected nodes and rules, no warnings
  3. Schema — every table, row, tree, binding, redirect and media record validates
  4. Reference integrity — no missing child, parent, root, class, component or template reference
  5. Archive routing — ZIP rejected at the JSON endpoint, accepted at the archive endpoint
  6. Full publish — site snapshot and page active versions created
  7. Row activation — a new post gets one version and renders; a changed post gets exactly one new version
  8. Stale-version regression — overwriting a published row must not leave the old version live
  9. Templates — unique priority winners, one outlet, shared component appears once
  10. Loops — blog index returns expected rows, order, limit and pagination
  11. Redirects — every expected redirect returns 301 with the correct target
  12. Resume — kill mid-run, resume with no duplicate versions
  13. Idempotency — the full second run is a real no-op
  14. Partial-release safety — force a mid-run failure, prove the report and the resume path
  15. Backup restore — the database dump plus uploads tree restores on a scratch target and reproduces the pre-change public hashes including published state. A bundle-export restore does not satisfy this and never did
  16. Live browser — desktop and 390px screenshots show correct structure and no overflow

Owner acceptance runs on a scratch tenant before any real target. Automated checks do not replace the final visible route and editor checks.
